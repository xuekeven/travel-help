# 12306 买票助手 · 需求文档

> 版本：v1.0  
> 日期：2026-05-17  
> 作者：个人项目

---

## 一、项目背景

本项目是一个面向个人使用的 12306 购票辅助工具，核心目标有两个：

1. **实用性**：解决每次抢火车票时"忘记开售时间"和"候补订单分散难管理"的问题
2. **学习性**：作为前端工程师向全栈 AI 应用方向转型的实践项目

---

| 属性 | 描述 |

| 使用环境 | 家庭自建服务器（旧电脑）部署，浏览器访问 |

## 三、名词解释

| 术语 | 说明 |
|------|------|
| **出行计划** | 用户预先登记的一次火车出行记录，包含出行日期、始发终到、座位类型等 |
| **开售日** | 12306 规则：出发日期往前推 14 天（即提前 15 天，当天算第 1 天），当日 08:00 开始售票 |
| **候补订单** | 在 12306 提交的候补购票申请，票源紧张时排队等待 |
| **节假日** | 出行日期如恰逢法定节假日（如劳动节、国庆节等），用于在通知中补充说明 |

## 四、功能需求

### 4.1 功能一：开售提醒

#### 4.1.1 触发时机

每日 **00:00（中国标准时间，Asia/Shanghai）** 自动执行定时任务，进行以下两项判断：

| 判断条件 | 通知内容示例 |
|----------|-------------|
| 今天 = 某出行计划的开售日前一天（出行日期 - 15 天） | "你预定了要买 2026年5月1日 周五（**劳动节**）北京南→天津南的火车票，**明天就要开售了**，请关注" |
| 今天 = 某出行计划的开售日（出行日期 - 14 天） | "你预定了要买 2026年6月3日 周三 北京西→邯郸东的火车票，**今天就要开售了**，请关注" |

> 说明：节假日名称为空时，通知中不出现括号及节假日内容。

#### 4.1.2 通知格式

```
你预定了要买{出行日期，格式：YYYY年MM月DD日}{星期几}{（节假日名称）}{始发站}到{终到站}的火车票，{今天/明天}就要开售了，请关注
```

#### 4.1.3 通知渠道

企业微信应用消息推送（接口文档后续提供）。

### 4.2 功能二：出行计划管理

#### 4.2.1 数据模型

```
出行计划（TravelPlan）
```

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `id` | UUID | 自动 | 主键 |
| `departure_date` | DATE | ✅ | 出行日期（坐车那天） |
| `holiday_name` | VARCHAR | ❌ | 节假日名称，如"劳动节"，为空时不展示 |
| `from_station` | VARCHAR | ✅ | 始发站，如"北京南站" |
| `to_station` | VARCHAR | ✅ | 终到站，如"天津南站" |
| `seat_type` | ENUM | ✅ | 座位类型：二等座 / 一等座 / 硬卧 / 软卧 / 硬座 / 无座 |
| `ticket_count` | INT | ✅ | 购票张数，默认 1 |
| `status` | ENUM | ✅ | 状态，见下方枚举 |
| `remark` | TEXT | ❌ | 备注 |
| `created_at` | TIMESTAMP | 自动 | 创建时间 |
| `updated_at` | TIMESTAMP | 自动 | 更新时间 |

**status 枚举值：**

| 枚举值 | 含义 |
|--------|------|
| `PENDING_SALE` | 待开售 |
| `ON_SALE` | 已开售（抢票中） |
| `WAITLISTED` | 候补中 |
| `SUCCESS` | 购票成功 |
| `FAILED` | 购票失败 |
| `CANCELLED` | 已取消 |

#### 4.2.2 功能列表

| 功能 | 说明 |
|------|------|
| 查看出行计划列表 | 以列表/卡片形式展示所有出行计划，支持按出行日期排序 |
| 新增出行计划 | 表单填写，提交后保存 |
| 编辑出行计划 | 修改任意字段 |
| 删除出行计划 | 物理删除，需二次确认 |

### 4.3 功能三：候补订单优化展示

#### 4.3.1 数据获取方式

使用 **Chrome Extension（浏览器插件）** 的方式获取候补订单数据。

> **选择理由（对比 Playwright）：**  
> - 插件直接复用用户已登录的 12306 真实会话，无需维护 Cookie/登录态  
> - 完全规避 12306 反爬机制（设备指纹、滑块验证等），不存在被封号风险  
> - 通过拦截 12306 候补订单页的 XHR/Fetch 响应获取数据，精准可靠  
> - 用户主动触发同步，点击一次即可刷新本地数据库

#### 4.3.2 数据模型

```
候补订单（WaitlistOrder）
```

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `id` | UUID | 自动 | 主键 |
| `order_no` | VARCHAR | ✅ | 12306 候补订单号（唯一键，用于 upsert） |
| `departure_date` | DATE | ✅ | 出发日期 |
| `from_station` | VARCHAR | ✅ | 始发站 |
| `to_station` | VARCHAR | ✅ | 终到站 |
| `train_numbers` | TEXT[] | ✅ | 候补的车次列表，如 ["G1", "G3", "G5"] |
| `seat_type` | VARCHAR | ✅ | 座位类型 |
| `ticket_count` | INT | ✅ | 候补张数 |
| `price` | DECIMAL | ✅ | 票价（元） |
| `departure_time` | TIME | ✅ | 出发时间（用于排序） |
| `arrival_time` | TIME | ✅ | 到达时间 |
| `status` | VARCHAR | ✅ | 候补状态（来自 12306，如"候补中"、"已成功"等） |
| `raw_data` | JSONB | ✅ | 原始数据，保留完整 JSON 供后续扩展 |
| `synced_at` | TIMESTAMP | 自动 | 最近一次同步时间 |
| `created_at` | TIMESTAMP | 自动 | 首次入库时间 |

#### 4.3.3 聚合展示逻辑

**聚合规则**：同一出发日期 + 相同始发站 + 相同终到站的多条候补订单，合并为一组展示。

**展示方式**：
- 组内每条候补订单独立展示（车次、座位、价格、出发时间等）
- 支持两种排序维度（组内排序）：
  - 出发时间 **早→晚**
  - 票价 **低→高**

#### 4.3.4 数据同步机制

| 步骤 | 说明 |
|------|------|
| 1 | 用户打开 12306 候补订单页面 |
| 2 | Chrome Extension 自动拦截该页面的候补订单 API 响应 |
| 3 | 插件解析数据，POST 到本地服务 `/api/waitlist/sync` |
| 4 | 后端以 `order_no` 为唯一键执行 **upsert**（已有则更新，没有则新增） |
| 5 | 前端刷新候补订单列表 |

## 六、非功能性需求

| 类别 | 要求 |
|------|------|
| **部署** | 家庭自建服务器，持续运行，局域网/公网均可访问 |
| **时区** | 所有时间处理均以 `Asia/Shanghai`（UTC+8）为准 |
| **安全** | 单用户个人工具，无需复杂权限体系；企微 Token 等敏感信息通过环境变量管理 |
| **可用性** | 定时任务具备基本的错误捕获和日志记录 |
| **浏览器支持** | Chrome Extension 只需支持 Chrome/Edge（Chromium 内核） |
