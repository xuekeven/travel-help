## 一、项目背景

本项目是一个面向个人使用的 12306 购票辅助工具，核心目标有两个：

1. **实用性**：解决每次抢火车票时"忘记开售时间"和"候补订单分散难管理"的问题
2. **学习性**：作为前端工程师向全栈 AI 应用方向转型的实践项目

## 三、名词解释


| 术语       | 说明                                           |
| -------- | -------------------------------------------- |
| **购票计划** | 用户预先登记的一次火车出行记录，包含出行日期、始发终到站、座位类型等           |
| **开售日**  | 12306 规则：出发日期往前推 14 天（即提前 15 天，当天算第 1 天）开始售票 |
| **候补订单** | 在 12306 提交的候补购票申请，票源紧张时排队等待                  |
| **节假日**  | 出行日期如恰逢法定节假日（如劳动节、国庆节等），用于在通知中补充说明           |

## 四、功能需求

### 4.1 功能一：购票提醒

#### 4.1.1 触发时机

每个开售时间生成两条持久化提醒任务。消费者每分钟只检查已到期任务：


| 判断条件                           | 通知内容示例                                        |
| ------------------------------ | --------------------------------------------- |
| 到达开售时间前 24 小时 | 发送“售前 24 小时”提醒 |
| 到达开售时间前 15 分钟 | 发送“售前 15 分钟”提醒 |


#### 4.1.2 通知格式

```
【{出行日期，格式：YYYY-MM-DD}】【{周几}】【{始发站}】到【{终到站}】的火车票，【{开售时间编号}：{开售时间}】，这是{售前 24 小时/售前 15 分钟}提醒，请关注
```

#### 4.1.3 通知渠道

企业微信应用消息推送。

#### 4.2.1 数据模型

```
购票计划（TravelPlan）
```


| 字段名              | 类型        | 必填  | 说明                                 |
| ---------------- | --------- | --- | ---------------------------------- |
| `id`             | UUID      | 自动  | 主键                                 |
| `departure_date` | DATE      | ✅   | 出行日期（坐车那天）                         |
| `sale_date` | TIMESTAMP | ✅   | 首个开售时间，新增计划时默认按出行日期提前 14 天的 08:00 生成，可修改 |
| `additional_sale_dates` | TIMESTAMP[] | ❌ | 额外开售时间，支持动态增加与删除 |
| `holiday_name`   | VARCHAR   | ❌   | 节假日信息，如"劳动节"，为空时不展示                |
| `from_station`   | VARCHAR   | ✅   | 始发站，如"北京南站"                        |
| `to_station`     | VARCHAR   | ✅   | 终到站，如"天津南站"                        |
| `seat_type`      | ENUM      | ✅   | 座位类型：二等座 / 一等座 / 硬卧 / 软卧 / 硬座 / 无座 |
| `ticket_count`   | INT       | ✅   | 购票张数，默认 1                          |
| `status`         | ENUM      | ✅   | 状态由首个开售时间自动计算，仅显示“待开售 / 已开售”         |
| `remark`         | TEXT      | ❌   | 备注                                 |
| `created_at`     | TIMESTAMP | 自动  | 创建时间                               |
| `updated_at`     | TIMESTAMP | 自动  | 更新时间                               |


**status 枚举值：**


| 枚举值            | 含义  |
| -------------- | --- |
| `PENDING_SALE` | 待开售 |
| `ON_SALE`      | 已开售 |


#### 4.2.2 功能列表


| 功能       | 说明                         |
| -------- | -------------------------- |
| 查看购票计划列表 | 以列表/卡片形式展示所有购票计划，支持按出行日期排序 |
| 新增购票计划   | 表单填写，状态自动计算后保存             |
| 编辑购票计划   | 修改任意字段，状态始终按首个开售时间自动重算       |

| 管理开售时间   | 首个开售时间默认提前 14 天的 08:00；可追加任意数量的日期和时间 |

### 4.3 功能三：候补订单优化展示

#### 4.3.1 数据获取方式

使用 **Chrome Extension（浏览器插件）** 的方式获取候补订单数据。

> **选择理由（对比 Playwright）：**  
>
> - 插件直接复用用户已登录的 12306 真实会话，无需维护 Cookie/登录态  
> - 完全规避 12306 反爬机制（设备指纹、滑块验证等），不存在被封号风险  
> - 通过拦截 12306 候补订单页的 XHR/Fetch 响应获取数据，精准可靠  
> - 用户主动触发同步，点击一次即可刷新本地数据库

#### 4.3.2 数据模型

```
候补订单（WaitlistOrder）
```


| 字段名              | 类型        | 必填  | 说明                           |
| ---------------- | --------- | --- | ---------------------------- |
| `id`             | UUID      | 自动  | 主键                           |
| `order_no`       | VARCHAR   | ✅   | 12306 候补订单号（唯一键，用于识别同一订单）    |
| `departure_date` | DATE      | ✅   | 出发日期                         |
| `from_station`   | VARCHAR   | ✅   | 始发站                          |
| `to_station`     | VARCHAR   | ✅   | 终到站                          |
| `train_numbers`  | TEXT[]    | ✅   | 候补的车次列表，如 ["G1", "G3", "G5"] |
| `seat_type`      | VARCHAR   | ✅   | 座位类型                         |
| `ticket_count`   | INT       | ✅   | 候补张数                         |
| `price`          | DECIMAL   | ✅   | 票价（元）                        |
| `departure_time` | TIME      | ✅   | 出发时间（用于排序）                   |
| `arrival_time`   | TIME      | ✅   | 到达时间                         |
| `status`         | VARCHAR   | ✅   | 候补状态（来自 12306 的原始状态文案）       |
| `raw_data`       | JSONB     | ✅   | 原始数据，保留完整 JSON 供后续扩展         |
| `synced_at`      | TIMESTAMP | 自动  | 最近一次同步时间                     |
| `created_at`     | TIMESTAMP | 自动  | 首次入库时间                       |


#### 4.3.3 聚合展示逻辑

**聚合规则**：同一出发日期 + 相同始发站 + 相同终到站的多条候补订单，合并为一组展示。

**展示方式**：

- 组内每条候补订单独立展示（车次、座位、价格、出发时间等）
- 支持两种排序维度（组内排序），每个维度都支持升序/降序切换：
  - 出发时间
  - 票价

#### 4.3.4 数据同步机制


| 步骤  | 说明                                            |
| --- | --------------------------------------------- |
| 1   | 用户打开 12306 候补订单页面                             |
| 2   | Chrome Extension 自动拦截该页面的候补订单 API 响应          |
| 3   | 插件解析数据，POST 到本地服务 `/api/waitlist/sync`        |
| 4   | 后端先清空当前候补数据，再按 `order_no` 重新写入最新数据（为空时也同步空数据） |
| 5   | 前端刷新候补订单列表                                    |


#### 4.3.5 候补订单提醒

同步候补订单时，为仍未成功、仍未取消的订单生成出行前 2 天、1 天和当天
**00:00（中国标准时间，Asia/Shanghai）** 的持久化任务。首次同步只补建计划时间未超过
30 分钟的任务；已经创建的失败任务在当天有效期内继续重试。

通知格式：

```
【{出行日期，格式：YYYY-MM-DD}】【{星期几}】【{始发站}】到【{终到站}】的候补订单还没有候补成功，还有{2/1}天就要出行了，请考虑【买长乘短、买短乘长、更换交通方式】等方案
【{出行日期，格式：YYYY-MM-DD}】【{星期几}】【{始发站}】到【{终到站}】的候补订单还没有候补成功，今天就要出行了，请考虑【买长乘短、买短乘长、更换交通方式】等方案
```

### 4.4 功能四：出行订单展示与提醒

新增「出行订单」模块，展示 12306「未出行订单」接口数据。模块位于「购票计划」和「候补订单」之间，数据由 Chrome 插件拦截 `https://kyfw.12306.cn/otn/queryOrder/queryMyOrder` 后同步。

设计原则：

- 按“订单”存储，一条 `OrderDTODataList` 入库一行。
- 保留 `tickets[]` 摘要，支持展示乘车人、座位类型、座位号、票价等多票信息。
- 插件同步前过滤「已退票」「已改签」「已出站」订单，仅向数据库推送有效未出行订单。
- 同步采用全量替换，空列表或过滤后无有效订单也同步为空数据并清空本地表。
- 同步时生成出行前 2 天、1 天、当天 00:00 的持久化提醒任务；首次同步只补建计划时间
  未超过 30 分钟的任务，已经创建的失败任务在当天有效期内继续重试。

表结构与接口说明见：[7.出行订单模块草案.md](7.出行订单模块草案.md)。

#### 4.4.1 提醒格式

```
【{出行日期，格式：YYYY-MM-DD}】【{星期几}】【{出发时间}】【{始发站}】到【{终到站}】的【{车次}】次列车还有{2/1}天就要出行了，乘车人：【{乘车人}】，座位：【{座位类型} {座位号}】，请提前安排出行
【{出行日期，格式：YYYY-MM-DD}】【{星期几}】【{出发时间}】【{始发站}】到【{终到站}】的【{车次}】次列车今天就要出行了，乘车人：【{乘车人}】，座位：【{座位类型} {座位号}】，请提前安排出行
```

## 六、非功能性需求


| 类别        | 要求                                            |
| --------- | --------------------------------------------- |
| **部署**    | 家庭自建服务器，持续运行，局域网可访问                           |
| **时区**    | 所有时间处理均以 `Asia/Shanghai`（UTC+8）为准             |
| **安全**    | 单用户个人工具，无需复杂权限体系；企微 Token 等敏感信息通过环境变量管理       |
| **可用性**   | 定时任务具备基本的错误捕获和日志记录                            |
| **浏览器支持** | Chrome Extension 只支持 Chrome/Edge（Chromium 内核） |
